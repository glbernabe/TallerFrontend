# Objective

This prompt must be used whenever existing code needs to be reviewed.

The objective is to evaluate the implementation against the project's architecture, coding standards and engineering principles before proposing any modifications.

The purpose is not to rewrite code.

The purpose is to identify strengths, weaknesses, risks and possible improvements.

---

# When to use this prompt

Use this prompt when:

- Reviewing a Pull Request.
- Reviewing your own implementation.
- Evaluating code generated by an AI.
- Evaluating code written by another developer.
- Reviewing legacy code.
- Verifying code quality before merging.

Do not use this prompt for:

- Bug fixing.
- Refactoring.
- Creating new features.

Dedicated prompts exist for those tasks.

---

# Philosophy

A good review is objective.

Never criticize code without explaining why.

Every observation must include:

- The problem.
- Why it is a problem.
- Its architectural impact.
- A possible improvement.

Avoid subjective opinions.

Always justify every recommendation.

---

# Mandatory workflow

## Step 1 — Understand the implementation

Before reviewing:

Explain:

- What the implementation does.
- Which feature it belongs to.
- Which layers are involved.
- What responsibilities each file has.

---

## Step 2 — Read project documentation

Always consult:

- `.ai/AGENT.md`
- `.ai/README.md`
- Relevant architecture chapters.
- Relevant templates.
- `coding-rules.md`

The review must always follow the documented standards.

---

## Step 3 — Review the implementation

Evaluate the following categories.

### Architecture

Verify:

- Clean Architecture.
- Layer separation.
- Dependency direction.
- Responsibility distribution.

---

### Components

Verify:

- Single Responsibility.
- Component size.
- Readability.
- Reusability.
- Composition.

---

### Hooks

Verify:

- Presentation logic only.
- No HTTP calls.
- Proper state management.
- Good separation from Components.

---

### UseCases

Verify:

- Single business responsibility.
- No React dependencies.
- Clear orchestration.

---

### Repository

Verify:

- No business logic.
- No DTO leakage.
- Proper abstraction.

---

### Services

Verify:

- Proper encapsulation.
- No duplicated API logic.
- Good separation.

---

### DTO

Verify:

- Correct external representation.
- Proper typing.

---

### Mapper

Verify:

- Pure transformations.
- No business logic.

---

### Domain

Verify:

- Independent from frameworks.
- Independent from Infrastructure.

---

### TypeScript

Verify:

- Strict typing.
- No unnecessary any.
- Correct generics.
- Descriptive types.

---

### React

Verify:

- Correct Hooks usage.
- Stable rendering.
- Proper memoization where needed.

---

### Performance

Verify:

- Unnecessary renders.
- Heavy calculations.
- Duplicate requests.
- Inefficient state updates.

---

### Accessibility

Verify:

- Semantic HTML.
- Keyboard accessibility.
- ARIA attributes when necessary.
- Image alt texts.

---

### Security

Verify:

- No secrets.
- Proper validation.
- Safe authentication flow.
- No exposed sensitive data.

---

### Maintainability

Verify:

- Naming.
- Folder organization.
- Readability.
- Consistency.
- Future scalability.

---

## Step 4 — Categorize findings

Every issue must have a severity.

### Critical

Must be fixed.

Examples:

- Architecture violation.
- Security issue.
- Broken authentication.
- Data corruption.

---

### High

Should be fixed.

Examples:

- Wrong responsibilities.
- Poor abstraction.
- High coupling.

---

### Medium

Recommended improvements.

Examples:

- Naming.
- Readability.
- Small refactors.

---

### Low

Optional improvements.

Examples:

- Formatting.
- Small simplifications.

---

## Step 5 — Suggest improvements

For every issue explain:

- Why.
- Impact.
- Recommended solution.

Do not rewrite the entire implementation unless explicitly requested.

---

# Things you must always verify

- Clean Architecture.
- SOLID.
- MVVM.
- Repository Pattern.
- Dependency Injection.
- Type Safety.
- Reusability.
- Documentation consistency.

---

# Things you must never do

Never:

- Criticize without justification.
- Suggest changes that contradict the project architecture.
- Recommend unnecessary abstractions.
- Rewrite working code without a clear benefit.
- Ignore project documentation.

---

## 6. Final Verdict

Choose one.

✅ Ready to merge.

⚠️ Merge after recommended improvements.

❌ Do not merge until critical issues are resolved.

---

# Definition of Done

A review is complete only when:

- Every relevant aspect has been evaluated.
- Every recommendation has been justified.
- Every critical issue has been identified.
- The implementation has been scored objectively.
- The final verdict is consistent with the findings.

Never provide a review without explaining the reasoning behind every important recommendation.
